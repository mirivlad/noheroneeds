# Работа с No Hero Needed

Сначала прочитайте актуальные `docs/STATUS.md`, затронутый код и принятые ADR.
Вносите только необходимые изменения, сохраняйте стиль проекта и чужие рабочие
файлы. Проверяйте причину ошибки и результат подходящими тестами. Не объявляйте
работу завершённой без свежих результатов проверки. Не сливайте PR и не создавайте
релиз без разрешения автора; инструкция текущей задачи имеет приоритет.

## Общие правила проверки и инструментов

- Не рефакторите и не форматируйте несвязанный код. Выбирайте наименьшее безопасное
  обратимое изменение; неоднозначность уточняйте, только если она мешает работе.
- Начинайте с локальных исходников, пакетов и поиска `rg`; Context7 используйте,
  когда важно актуальное поведение API. Проверки сначала направленные, затем
  обязательные выпускные.
- Для нетривиальных Go/TypeScript изменений используйте LSP-диагностику; при
  изменении общего состояния/идентичности/синхронизации/хранения — определения
  и ссылки LSP. Для простого текста и CSS LSP не требуется.
- Браузер нужен для существенной UI-проверки. Доступ к авторизованным браузерным
  сеансам допустим только по явному запросу пользователя.
- В отчёте укажите изменения, фактическую проверку и оставшуюся неопределённость.

## Обязательная документация игровых изменений

1. Новая механика, действие или контент требуют актуальной страницы вики в том же
   изменении. Игровая задача не завершена без соответствующей документации.
2. Каталог предметов, рецептов, источников, NPC, экипировки и торговли создаётся
   из игровых JSON командой `python3 tools/site/build.py`. Не редактируйте копию
   каталога вручную. Новые ID должны обнаруживаться автоматически.
3. При изменении поведения пересмотрите и обновите редакционное руководство в
   `site/content/guides/`, а не только каталог. Новую систему внесите в
   `site/mechanics-manifest.json` с явными путями к её коду и руководству.
4. Каждое заметное игроку изменение, включая исправления, отражайте в подготовленном
   `docs/changelog/`. Оформляйте запись `docs/changes/*.json`: реальные изменённые
   файлы и их SHA-256, затронутые механики, проверенные руководства и changelog.
5. До релиза обязательны генерация сайта, проверка документации/версии/ссылок,
   игровые и браузерные тесты и готовые пользовательские патчноуты. Не обходите
   зависимость `packages` от этих проверок ни для тега, ни для ручного workflow.
6. Исключение `no-player-facing-change` допустимо для чисто внутреннего изменения
   с конкретным обоснованием и точными хешами файлов. Для крупного изменения нужны
   также явный контракт сохранённого поведения и существующие регрессионные тесты;
   править пользовательское руководство без изменения поведения не требуется.
   Семантическое изменение контента этим исключением не закрывается.

Формат записей, команды и граница публичного сайта: `docs/WIKI_WORKFLOW.md`.
Публичный сайт собирается по опубликованному релизу; будущие возможности из
`main` могут показываться только в явно обозначенном предпросмотре.

## Порядок выпуска: вики и сайт раньше релиза

- Каждый **игровой релиз** готовится вместе с актуальной вики. Сначала сверяйте
  новые механики и исправления с кодом и JSON-контентом, затем обновляйте
  `site/content/guides/`, `site/mechanics-manifest.json`, журнал изменений
  `docs/changelog/vX.Y.Z.json` и подтверждения `docs/changes/*.json`.
  Даже если новые определения попадают в генерируемый каталог автоматически,
  изменение поведения должно быть отражено в пользовательском руководстве.
- До создания тега обязательны `python3 tools/site/build.py`, документационный
  барьер `tools/site/check.py --release vX.Y.Z`, тесты сайта/браузера
  (`tools/site/test.sh`) и игровые тесты (`tools/run_tests.sh`). Исправляйте
  причины ошибок; нельзя отключать или обходить release-gate ради выпуска.
- `release.yml` должен собрать игровые пакеты, GitHub Release и опубликованную
  версию вики **из одного проверенного релизного снимка**. После публикации
  убедитесь, что `/noheroneeds/` показывает именно последний опубликованный
  релиз, включая страницу обновлений и руководства, без содержимого будущих
  незавершённых изменений.
- При изменениях генератора сайта и выпускного процесса сохраняйте существующие
  дизайн, HTML/CSS и стили; правила `site/AGENTS.md` обязательны. Отдельное
  улучшение сайта или новая версия игры не дают права на незапрошенный редизайн.
- Не помечайте релиз завершённым до подтверждения успешных проверок, появления
  артефактов и публикации правильного снимка вики. При блокирующей ошибке
  остановитесь, сообщите причину и не создавайте обходной релиз.

## Где и когда выполняются тесты

- Для обычных коммитов, push и merge **не запускайте GitHub Actions CI**:
  разработчик или агент выполняет подходящие локальные тесты и записывает
  команды и результат в отчёт к изменению. Изменения игрового кода требуют
  соответствующих регрессионных тестов, изменения вики — локального
  `tools/site/test.sh` и проверки `tools/site/check.py`.
- Перед merge в `main` обязательна локальная проверка затронутых систем,
  включая повторную проверку после устранения конфликтов интеграции. Полный
  локальный прогон `TEST_TIMEOUT=2400 tools/run_tests.sh` нужен для больших
  игровых изменений; быстрые правки могут проверяться профильными тестами.
- **Полный GitHub CI запускается только при релизе**: `release.yml` вызывает
  `tests.yml` и `site-check.yml` один раз на один релизный workflow,
  затем выпускает пакеты и обновляет опубликованную вики только при успехе.
  Самостоятельные push/PR/tag-события не запускают повторные тесты.
- Ошибка/тайм-аут релизного CI блокирует публикацию. Запрещено отключать тесты,
  подменять их статус или публиковать релиз при красной проверке.
- GitHub Actions не может подтвердить факт локальных проверок сам по себе:
  агент указывает реально исполненные команды, окружение и результаты.
