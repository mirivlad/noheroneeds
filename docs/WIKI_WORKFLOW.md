# Вики как часть игровой задачи

Корневой `AGENTS.md` обязателен для Codex и других агентов. Игровое изменение
не завершено без каталога, актуального руководства и пользовательских патчноутов.

## Данные и редактура

`python3 tools/site/build.py` читает все пакеты `content/**/pack.json`, проверяет
пространства имён и ссылки, формирует записи, связи в обе стороны и поисковый
индекс. Результат — `build/site/`, он не хранится как вторая ручная база предметов.
Стабильный адрес записи: `wiki.html?item=base%3Airon_ore`.

Рецепты, ингредиенты, выходы, станции, учителя, цены/условия обучения, ассортимент,
добыча, существа, растения, конструкции, месторождения и другие игровые определения
берутся из JSON. Ребро связи хранит источник и JSON Pointer. Связи зданий таверн
с общей службой обслуживания — небольшой адаптер подтверждённого поведения
`Hospitality` с указанием символа GDScript. При неоднозначности нескольких профилей
эта связь не выдумывается. Веса добычи не выдаются за количества или проценты.

Визуальные/звуковые определения и варианты внешности проверяются на ссылки,
но не засоряют игровой каталог. Служебные шаблоны летописи без поручений
также не выдаются за самостоятельные игровые предметы или задания. Неизвестный новый тип данных требует явной
поддержки генератора и карты механик вместо молчаливого пропуска.

`site/content/guides/*.html` — редакционные главы. Они объясняют действия,
ограничения и поведение. Ссылки на сущности проверяются. Числа услуг таверны
вставляются шаблонами из игрового JSON; общие правила аренды и поведения написаны
вручную по коду. При изменении поведения обновляйте соответствующую главу.

## Запись проверки изменения

Создайте новый JSON в `docs/changes/`:

```json
{
  "changes": [{
    "impact": "player-facing-change",
    "summary": "Конкретное описание изменённого игрового сценария для человека.",
    "sources": {"src/server/hospitality.gd": "SHA256 текущего файла"},
    "mechanics": ["hospitality"],
    "guides": {"site/content/guides/hospitality.html": "SHA256 проверенного руководства"},
    "changelog": "docs/changelog/unreleased.json"
  }]
}
```

Получить SHA-256: `sha256sum ПУТЬ`. Карта `site/mechanics-manifest.json` связывает
механики с кодом и руководствами. Новому подсистемному файлу нужна явная запись
в карте. Хеш привязывает проверку к конкретному содержимому; последующая правка
кода требует нового подтверждения. Изменение поведения GDScript требует реальной
правки текста руководства: неизменённая глава или изменение только оформления
не принимается. Для изменения только данных достаточно проверки актуальных
генерируемых сведений и явного пересмотра соответствующей главы.

Запись должна входить в тот же PR. Старое подтверждение из предыдущего PR
не закрывает новое изменение. При проверке будущего релиза рассматривается
весь диапазон от предыдущей опубликованной версии; более поздние записи могут
замещать хеши ранних PR. Удалённый игровой файл обозначается хешем `deleted`.

Исключение `no-player-facing-change` содержит конкретное поле `rationale`
не менее 100 символов и точные хеши. Одна запись ограничена пятью файлами;
семантический JSON-контент исключать нельзя. Для правки свыше 100 строк добавьте
`internal_review`: `behavior_contract` с конкретными сохранёнными условиями
(не менее 100 символов) и `tests` — пути к существующим GDScript-тестам
в `tests/unit/`, которые выполняет игровой CI. Крупная внутренняя правка
не требует выдумывать пользовательское изменение или править неизменившееся
руководство, но требует более подробного подтверждения. Это не обход
документации новой механики. Пример
обоснованного исключения — `docs/changes/wiki-build.json`.

## Патчноуты и версия

`docs/changelog/vX.Y.Z.json` содержит `version`, `title`, `tagline`, `groups`
(заголовки и содержательные игровые пункты) и точную ссылку на GitHub Release.
В changelog укажите также `mechanics`: IDs из карты должны соответствовать
записи проверки изменения. Во время разработки можно использовать `unreleased.json`; перед тегом текст
переносится в файл конкретной версии. Пустой, технический или отсутствующий
changelog блокирует релиз. `release_notes.py` публикует именно подготовленный
текст вместо автоматического списка технических коммитов.

`sync_releases.py` получает действительные опубликованные Releases через API.
Черновики, prerelease и теги без Releases не включаются. Для офлайн-сборки
есть подтверждённый исторический снимок `site/content/published-releases.json`.
CI получает свежие данные, поэтому тест не закрепляет вечную последнюю версию.
Даты сайта отображаются в часовом поясе Asia/Irkutsk.

## Проверки

```sh
python3 -m pip install -r tools/site/requirements.txt
python3 tools/site/sync_releases.py
python3 tools/site/check.py --base origin/main --published build/published-releases.json
python3 -m unittest discover -s tools/site/tests -v
npm ci --prefix site
(cd site && npx playwright install chromium && npm test)
tools/run_tests.sh
```

Для выпуска: `python3 tools/site/check.py --release vX.Y.Z --published
build/published-releases.json`. Проверяются обе версии игры, changelog,
ссылки/обратные связи, покрытие механик, хеши проверки и построенный сайт.
Workflow `release` запускает документационный барьер с браузерными тестами и
игровые тесты; `packages` зависит от обоих. Это действует для тега и ручного
`workflow_dispatch`. Выпускной режим `--unpublished` также запрещает переупаковку
и перезапись уже опубликованной версии. Наличие тега не разрешает обойти сборочный барьер.

## Предпросмотр и публичная версия

`python3 tools/site/serve.py` показывает `build/site/` по адресу
`http://127.0.0.1:18764/noheroneeds/`. Это предпросмотр рабочей ветки.
В PR workflow прикладывает готовый статический сайт, снимки и отчёт Playwright.

Публично развёртывается **только** `tools/site/publish.py`: он выбирает последний
действительно опубликованный тег и собирает его игровые данные и документацию.
Новый текст из `main` туда не подмешивается. Метаданные `data/publication.json`
сохраняют оба точных SHA. Для исторического v0.17.0, где ещё не было сайта,
`site/publication.json` закрепляет отдельный неизменяемый коммит документации.
Последующие теги уже содержат сайт и собираются полностью из своего снимка.

Pages workflow запускается при `push main`, человеческом `release: published`
и вручную; публикация игры дополнительно явно вызывает тот же workflow после
успешного выпуска. Это необходимо, поскольку события обычного `GITHUB_TOKEN`
не запускают произвольные новые workflow:
[правило GitHub](https://docs.github.com/en/actions/how-tos/write-workflows/choose-when-workflows-run/trigger-a-workflow).
Черновой релиз из `workflow_dispatch` не публикует будущую вики.

## Настройка владельцем репозитория

После проверки PR:

1. Repository **Settings → Pages → Build and deployment → Source → GitHub Actions**.
   Сейчас используется старый режим ветки `feat/game-site-wiki`, корень `/`.
2. **Settings → Environments → github-pages → Deployment branches and tags**:
   в текущем режиме Selected branches and tags разрешена только
   `feat/game-site-wiki`. Добавьте правило **Branch: main** и правило
   **Tag: v*.*.***. Это разрешит публикацию после слияния и после игрового тега;
   ветку предпросмотра разрешать не требуется.
3. Разрешить слияние PR в `main` обычным способом. Сам агент этого не делает.
4. Проверить workflow **Published wiki**. При необходимости выбрать **Run workflow**
   на `main`; он всё равно соберёт опубликованный тег, а не будущую игру из main.
5. Проверить `https://mirivlad.github.io/noheroneeds/` и
   `/noheroneeds/data/publication.json`. В адресе не должно быть `/site/`.

До успешного deploy и проверки HTTP/браузера новый публичный сайт не считается
опубликованным. Настройки Pages и опубликованные игровые Releases эта задача
не меняет.
