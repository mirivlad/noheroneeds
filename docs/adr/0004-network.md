# ADR-0004 — Сеть: MultiplayerAPI + ENet как транспорт, свои сообщения и репликация

**Статус:** принято автором 14.10.2026. Основание: `docs/proposals/002-network-storage-identity.md`, вариант N2.

## Решение

1. **Транспорт — `MultiplayerAPI` Godot с `ENetMultiplayerPeer`.** Соединения, надёжность, порядок, фрагментацию и каналы делает ENet.
2. **Над транспортом — наши сообщения, репликация, интерес-менеджмент.** Серверная симуляция не зависит от дерева сцен (ADR-0002). Встроенные `MultiplayerSpawner`/`MultiplayerSynchronizer` для состояния мира не используются.
3. **Версионирование протокола.** Каждое соединение начинается рукопожатием: версия протокола, отпечаток набора контента, вход по ключу (ADR-0006). Несовместимая версия — понятный отказ, а не порча состояния. Каждое сообщение несёт тип; форматы сообщений меняются только с повышением версии протокола.
4. **Критические операции доставляются надёжно и идемпотентно.** Строительство, передача и крафт предметов, урон по постройкам, переходы между локациями идут надёжным упорядоченным каналом с `request_id`. Сервер помнит обработанные `request_id`: повтор возвращает прежний результат. Подтверждение клиенту — только после фиксации в хранилище (ADR-0005).
5. **Отдельные каналы:**
   - 0 — надёжный упорядоченный: запросы, ответы, события;
   - 1 — ненадёжный последовательный: оперативное состояние (снимки движения), устаревшее отбрасывается;
   - 2 — надёжный, низкий приоритет: потоковая выдача чанков и локаций.
6. **Транспорт заменяем.** Тот же слой сообщений работает поверх транспорта в памяти (тесты, одиночная игра) и поверх ENet.

## Последствия

- Репликацию (снимки, дельты, интерес «крыша ↔ улица») пишем сами — это ядро сетевой части игры.
- Тесты: транспорт в памяти с N клиентами; настоящий ENet на localhost; нагрузочный стенд с замерами.

## Реализация (14.10.2026)

- **Транспорт** — `ENetMultiplayerPeer`, используемый напрямую через интерфейс `MultiplayerPeer` (пакеты, каналы, режимы доставки). RPC и `SceneMultiplayer` не нужны: сервер работает без дерева сцен. `RELIABLE` и `STATE` идут по каналу 0 ENet (надёжный и ненадёжный трафик там разделены), `BULK` — по своему каналу 1.
- **Транспорт в памяти** (`MemoryTransport`) — для тестов и одиночной игры (`LocalGame`: тот же сервер в процессе). Умеет терять, дублировать и переставлять пакеты `STATE` и задерживать всё.
- **Протокол** (`Protocol`, версия 1) — CBOR-сообщения с проверкой каждого поля при разборе. Вход: `HELLO` (версия, отпечаток контента, ключ) → `CHALLENGE` (случайный вызов, ID сервера) → `AUTH` (подпись вызова, привязанная к ID сервера и игрока) → `JOIN` (подписанный профиль) → `WELCOME`. Несовместимая версия или контент — `REJECT` с причиной.
- **Движение** — общий для сервера и клиента целочисленный код (1/256 клетки), поэтому предсказание клиента совпадает с сервером точно. Клиент повторяет последние 4 ввода в каждом пакете и сверяется со снимками.
- **Снимки** (протокол 7, 15.10.2026) — разница с тем, что клиент подтвердил. Сервер держит на каждую сессию подтверждённые версии сущностей и для каждого неподтверждённого снимка — что в нём ушло. Подтверждение снимка N переносит его содержимое в подтверждённое; каждый снимок несёт все ещё не подтверждённые отличия (в пределах размера пакета), поэтому потеря, дубль и перестановка ничего не ломают. Клиент применяет только снимок новее последнего — к своему единственному состоянию, без копий.
  - Состояние сущностей (реплики) общее для всех клиентов: «горячая» часть (позиция) и «холодная» (вид, имя, внешность), у каждой своя версия; реплики обновляются на месте.
  - Позиции уходят упакованными `int32 [номер, x, y]` в поле `hot`, удалённые — `int32` в `removed`; целиком (с полным ID) — только сущность, новая для клиента; изменения «холодной» части и свой инвентарь — словарём. Удаление повторяется, пока не подтверждено; вернувшаяся сущность приходит целиком.
  - Обзор сессии (персонажи, предметы, существа вокруг) пересчитывается раз в 4 тика (у каждой сессии свой такт), при переходе игрока в другую клетку сетки 8×8 и при изменении предметов; реплики существ разложены по постоянной сетке и обновляются только у тех, кто сдвинулся.
  - Сущности в снимке обозначены короткими номерами соединения; полный ID приходит один раз (протокол v3).
  - Сообщения кодируются быстрым CBOR без сортировки ключей. Детерминированный CBOR остаётся для подписей и хранения.
  - Замеры: `docs/measurements/2026-10-14-load.md`, `2026-10-14-creatures-load.md`, `2026-10-15-tick-peaks.md`.
- **Интерес** — пока радиус в чанках в той же локации; правила крыш и закрытых этажей придут со строительством.
- **Чанки** — по `BULK`, ближние первыми, не больше 4 за тик на клиента, при каждой ревизии чанка.
- **Запросы** — результат приходит после фиксации. Клиент повторяет неотвеченные запросы после переподключения; сервер применяет их один раз.
- **Персонаж в мире.** При первом приходе профиль становится копией мира, инвентарь переходит в инвентари мира. Повторный вход берёт копию мира и проверяет владельца. Что делает второй сервер с персонажем, известным по другому миру, — по-прежнему Q-01.
- **Выделенный сервер** — `tools/run_server.sh`. Остановка: команда `stop` в консоли или файл `STOP` рядом с миром. SIGTERM Godot обрабатывает мгновенным выходом: подтверждённое при этом не теряется, но последние позиции могут не записаться.
