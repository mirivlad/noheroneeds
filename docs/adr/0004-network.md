# ADR-0004 — Сеть: MultiplayerAPI + ENet как транспорт, свои сообщения и репликация

**Статус:** принято автором 14.10.2026. Основание: `docs/proposals/002-network-storage-identity.md`, вариант N2.

## Решение

1. **Транспорт — `MultiplayerAPI` Godot с `ENetMultiplayerPeer`.** Соединения, надёжность, порядок, фрагментацию и каналы делает ENet.
2. **Над транспортом — наши сообщения, репликация, интерес-менеджмент.** Серверная симуляция не зависит от дерева сцен (ADR-0002). Встроенные `MultiplayerSpawner`/`MultiplayerSynchronizer` для состояния мира не используются.
3. **Версионирование протокола.** Каждое соединение начинается рукопожатием: версия протокола, отпечаток набора контента, вход по ключу (ADR-0006). Несовместимая версия — понятный отказ, а не порча состояния. Каждое сообщение несёт тип; форматы сообщений меняются только с повышением версии протокола.
4. **Критические операции доставляются надёжно и идемпотентно.** Строительство, передача и крафт предметов, урон по постройкам, переходы между локациями идут надёжным упорядоченным каналом с `request_id`. Сервер помнит обработанные `request_id`: повтор возвращает прежний результат. Подтверждение клиенту — только после фиксации в хранилище (ADR-0005).
5. **Отдельные каналы:**
   - 0 — надёжный упорядоченный: запросы, ответы, события;
   - 1 — ненадёжный последовательный: оперативное состояние (снимки движения), устаревшее отбрасывается;
   - 2 — надёжный, низкий приоритет: потоковая выдача чанков и локаций.
6. **Транспорт заменяем.** Тот же слой сообщений работает поверх транспорта в памяти (тесты, одиночная игра) и поверх ENet.

## Последствия

- Репликацию (снимки, дельты, интерес «крыша ↔ улица») пишем сами — это ядро сетевой части игры.
- Тесты: транспорт в памяти с N клиентами; настоящий ENet на localhost; нагрузочный стенд с замерами.
