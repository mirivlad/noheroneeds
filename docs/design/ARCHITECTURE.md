# No Hero Needed — архитектурные ориентиры · v0.2

> Этот документ — **предложение технической модели** для обсуждения с Claude, а не готовое решение о конкретных классах, плагинах или фреймворке. В случае конфликта приоритет у `GDD.md`.

## 1. Цели архитектуры

1. Новый самостоятельный **2D Godot 4.x** проект. 3D-наследия нет.
2. Продолжаемое годами развитие игрового мира и механик без гигантского монолита.
3. Выделенный сервер, авторитетный расчёт игрового состояния, одиночный режим по совместимой модели.
4. Переносимые персонажи с редактором внешности и независимыми от мира данными.
5. Чанковая поверхность и много отдельных постоянных `Location` с переходами.
6. Взаимодействие крыши и поверхности, хотя игровые сцены верхних этажей раздельны.
7. Версионированные сохранения и миграции: обжитые миры нельзя уничтожать обновлением.
8. Контент определяется данными; возможность расширений/модов сохраняется без преждевременного универсального плагинного движка.

## 2. Предлагаемые границы подсистем

| Область | Отвечает за | Не должна зависеть от |
|---|---|---|
| `simulation` | Сущности, компоненты/свойства, время, правила взаимодействий, тики | Камера, GUI |
| `world` | Seed, чанки, биомы, существующие модификации карты | Активная сцена конкретного клиента |
| `locations` | ID локаций, этажи, пещеры, переходы, генерация один раз | Отображаемый игроком номер Z |
| `building` | Стены, перекрытия, крыши, опоры, разрушения, право на модификацию | Механизм отрисовки спрайтов |
| `perception` | Обзор, препятствия, знание целей, наружная проекция с крыш | Видимость текстур на клиенте |
| `combat` | Валидация атаки, дистанция, направление, повреждения | Клиентские hitbox-решения как окончательная истина |
| `characters` | Переносимый персонаж, внешний вид, навыки, экипировка | Координаты конкретного мира как часть профиля |
| `world_characters` | Местное положение, репутации, привязка к недвижимости | Изменяемость глобального шаблона персонажа |
| `content` | Материалы, предметы, рецепты, биомы, NPC, диалоги, идентификаторы | Конкретные имена, захардкоженные в логике |
| `network` | Подключения, авторитет сервера, RPC, области подписки, политика доступа | Слои GUI как источник данных |
| `persistence` | Снимки, журнал изменений, версии, миграции, бэкапы | Текущий способ рендера |
| `presentation` | Тайлы, спрайты, слои персонажей, камера, звук, GUI | Решение о результатах игрового действия |

Названия примерные. Не пытаться создавать все директории и абстракции прежде, чем появятся работающие реальные случаи.

## 3. Канонические сущности (концептуальные, не жёсткая схема)

```text
World:
  world_id, seed, generation_version, sim_time, rules, state_revision

Chunk:
  world_id, chunk_coord, base_generation_ref, edited_cells, persistent_entities

Location:
  location_id (UUID), world_id, type, parent_ref?, z_label,
  generation_seed?, generation_version?, generated_once, stored_state

Portal:
  portal_id, origin_location, origin_region, target_location,
  target_spawn, allowed_travel, access_policy

Building:
  building_id, world_id, footprint, owner_acl,
  walls, doors, floors, roof_parts, exposed_positions, level_location_ids

Entity:
  entity_id, prototype_id, location_id, position,
  properties, current_state, schema_version

PortableCharacter:
  character_id, schema_version, creator/ownership_proof,
  identity, appearance, progression, recipes, inventory, equipment,
  content_manifest, transfer_metadata

WorldCharacterState:
  world_id, character_id, current_location, position,
  local_reputation, world_permissions, personal_world_flags
```

**Непременный инвариант:** `z_label` — цифра в интерфейсе, не идентификатор. Подвал двух таверн с `−1` — разные `location_id`.

## 4. События и инварианты

Пример взаимодействия (не требование использовать именно event bus):

```text
PlayerRequestBuild(wall, cell, material)
  -> ServerValidate(resources, position, rights, collision, support)
  -> ApplyWorldMutation
  -> PersistMutation / transaction or write-ahead journal
  -> Emit(BuildingPartPlaced)
  -> Recalculate affected traversal/visibility/roof regions
  -> Broadcast to interested clients
```

Не должно получиться двух стен за один комплект ресурсов из-за повторного пакета. Аналогично с выдачей предметов, урона, приёмом переносимых персонажей.

Время симуляции — явное и тестируемое; независимые системы не должны молча полагаться на частоту кадров GUI. Для удалённых областей допустима агрегированная/отложенная симуляция при наличии определённых правил её воспроизводимости.

## 5. Поверхность, этажи и крыши

- **Поверхность Z=0:** единые координаты/чанки, первый этаж встроен туда же, дверь дома не должна обязательно телепортировать в отдельную сцену.
- **Внутренние верхние этажи:** отдельные `Location`, виден один активный уровень, переход по `Portal` (лестница, лифт, люк).
- **Крыша и боевые настилы:** имеют местоположение и высоту относительно основной карты, принадлежат зданию/локации; их видимая наружная область проецируется на окрестные чанки поверхности.
- **Перекрытие:** создаёт допустимую область для будущего верхнего уровня; стены без перекрытия не создают этаж. Кровля — отдельное свойство.
- **Прямое межуровневое взаимодействие:** сервер умеет проверить выстрел, обзор, падение и вражеский поиск пути. Не подменять геометрию рендера «высотой» и наоборот.
- **Подземелья:** `generated_once`, seed+версия алгоритма, постоянный snapshot/delta. Изменение генератора не переписывает существующую пещеру. Для воспроизводимости, если старый алгоритм удалён, нужна независимая каноническая сериализация сформированной геометрии (или хранение данных, достаточных без старого генератора).

## 6. Персонаж и перенос между серверами

### 6.1. Внешность

Слои тела, одежды, волос и снаряжения состоят из комбинации выбранных параметров и содержимого инвентаря. Имя `appearance_style_id` должно быть стабильным. Запрещено строить сохранение только на индексах массивов и пути к texture-файлу, потому что контент изменится.

### 6.2. Профиль, мир и экземпляр

`PortableCharacter` — каноническое переносимое содержимое, `WorldCharacterState` — локальные связи мира, права, репутация и положение. Не путать `character_id` и текущий сетевой `player_peer_id`.

### 6.3. Набросок импортного контракта

```json
{
  "format": "nhn.character",
  "schema_version": 1,
  "character_id": "uuid-placeholder",
  "identity": {"name": "Example"},
  "appearance": {"style_id": "default:human", "parameters": {}},
  "progression": {},
  "inventory": [],
  "equipment": {},
  "known_recipes": [],
  "content_manifest": {"packs": []},
  "transfer": {"mode": "UNDECIDED", "origin": null}
}
```

Это **иллюстрация полей, не окончательная реализация и не повод фиксировать `mode`**. Экспорт с произвольного клиента считается недоверенным. Принимающий сервер валидирует идентификаторы предметов, допустимость содержимого, совместимость версий и политику доверия. Для гарантии уникальности требуется согласованная контролируемая передача через доверенную инфраструктуру; между недоверенными частными серверами абсолютную неклонируемость обеспечить нельзя. Семантика «переезд или копирование» пока не решена.

### 6.4. Атомарность миграции

Если в будущем выбран эксклюзивный переезд, разумный механизм — транзакция `prepare -> receive -> commit` с lease/блокировкой на отправляющей стороне, idempotency key, квитанцией и восстановлением после сбоев. Режим дублируемых копий будет иметь иной протокол; **не решать выбор молча**.

## 7. Расширение, моды, версии

- Предпочитать явные stable identifiers вроде `base:oak_log`, `base:stone_wall`, `base:recipe_bread` вместо логики по отображаемому названию.
- Каждый контент-пакет объявляет ID, версию и зависимости; коллизии ID запрещены. Как разрешается отсутствие контента при миграции — открытый вопрос.
- Системы могут объявлять поддерживаемые свойства/действия, но сложный универсальный API модификаций — отдельное инженерное решение.
- Изменения формата мира и персонажей сопровождать схемой миграции и тестом восстановления; обновления генератора не должны затрагивать сформированные посещённые подземелья и изменённые чанки.
- Документировать принятое решение ADR, когда архитектура затрагивает несколько подсистем или необратимость данных.

## 8. Тестирование и качество

- Автоматические тесты сохранения/загрузки, детерминизма чанков, постоянства подземелий.
- Сценарии против дублирования вещей и построек из повторных/конкурирующих клиентских запросов.
- Проверки видимости и атак между закрытым этажом, крышей и улицей; проверка NPC знания о цели.
- Импорт персонажа: корректный, повреждённый, несовместимый и с неизвестным предметом.
- Репликация двух игроков и стресс-тест имитированных 10–20 клиентов **с фактическими замерами**.
- Снимки/восстановление миров после обновления схемы.

## 9. Что НЕ следует делать

- Переносить или восстанавливать удалённый 3D-код.
- Называть небольшой технический эксперимент «MVP» и на этом сокращать видение игры.
- Заводить единый `GameManager`, в котором решается всё: жизнь NPC, экономика, стрельба, рендер, сохранения и транспорт.
- Сохранять персонажа только внутри файла мира.
- Хранить постоянную пещеру только через seed без версии/гарантии восстановления сформированного состояния.
- Выполнять проверки инвентаря и боевых результатов исключительно на клиенте.
- Объявлять «готово» без испытания перезапуска мира и сетевой согласованности затронутого механизма.
