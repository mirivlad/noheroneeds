# Эксперимент 960×540 — 17 октября 2026

> **20.10.2026, уборка:** исходные захваты окна, маски, логи и JSON-замеры этого отчёта не перенесены в основную историю (десятки мегабайт). Они лежат в ветке `codex/character-art-production-01`, коммит `f9bf7e1`; ссылки ниже на них ведут туда, а не в рабочую копию.

**Исторический отчёт первого эксперимента.** Последующим решением пользователя
HD принят как основной и включён по умолчанию: [Visual Standard HD](../../art/visual_standard_hd.md),
[ADR-0022](../../adr/0022-hd-visual-baseline.md). Упоминания legacy как default
ниже относятся к проверенному тогда коммиту `99423b7`.

960×540 подходит как техническая основа для следующего этапа графики.
При camera zoom 2 клетка занимает 32 логических пикселя, обзорность остаётся
30×16,875 клетки, координаты сервера и физика остаются прежними. Режим экспериментальный;
по умолчанию игра использует legacy. Новая графика не создавалась.

## Переключение

```sh
tools/run_game.sh --display=hd
tools/run_game.sh --display=legacy
```

Параметр действует на весь запуск, включая меню. Настройка не записывается в профиль.
Для личного просмотра без использования основного профиля можно добавить
`--profile=display-review` и создать/загрузить мир через обычное меню.
Переключение требует перезапуска. `project.godot` сохранён без изменений.

## Аудит настоящего пути отображения

- `project.godot`: viewport 480×270, желаемое **клиентское** окно 1920×1080,
  stretch `viewport`, scale mode `integer`, Compatibility renderer, nearest (`0`).
  Нативное окно — корневой `Window`, он же корневой viewport.
- `scenes/main.tscn` запускает `App`; тот создаёт настоящий `GameScreen`, локальный
  сервер либо сетевого клиента. В игровом пути нет промежуточного `SubViewport`,
  `SubViewportContainer` или картинки, искусственно вписанной в окно.
- `GameSettings.apply()` переключает fullscreen через DisplayServer и меняет vsync,
  но не назначает логическое разрешение. Режим окна меняется только при необходимости.
- `GameScreen` создаёт единственную `Camera2D`: smoothing выключен,
  `view_zoom=1` обычно и `0,75` для отдаления. Камера следует округлённой позиции
  игрока; `CharacterSprite.show_at()` тоже округляет положение ног.
- `WorldView.CELL=16`: это **мировые координаты презентации**, не размер окна.
  `Movement.UNIT=256`, коллайдер ног ±80/±48 единиц, ход 51 единица за тик,
  диагональ 36, частота 20 Гц. Преобразование симуляции в мир: 16 единиц на мировой пиксель.
  Эти числа и код движения, сервера, взаимодействий, сети и хранения не менялись.
- `WorldView.setup()` задаёт TileSet и регионы плоских атласов 16×16.
  Размеры высоких объектов, origin, rotations и варианты берутся из визуальных
  определений `content/base/*.json`, рисуются тем же WorldView с прежним Y-sort.
- `CharacterSprite` берёт размер кадра, origin и `pixel_scale` из контента.
  В проверке использован существующий `base:human_m`: источник 96×96,
  слои scale 0,5, origin (48,90), одежда из обычного стартового комплекта.
  Прямоугольник кадра в мире 48×48; это не видимый рост персонажа.
- HUD и меню находятся в `CanvasLayer`, поэтому zoom камеры на них не действует.
  В старом HUD найдены привязки к 480: миникарта x=404, хотбар около центра x=240,
  status y=252. Кроме того, длинные Label не ограничивали ширину и уходили за экран.
  У инвентаря и окна персонажа остаются локальные фиксированные размеры
  300×170 и ширина 456, но они помещаются в оба viewport. Карта мира уже использует
  anchors и свой `size`, меню — anchors и CenterContainer.
- Базовый font size HUD 16, слот хотбара 20×20, миникарта 72×72 логических пикселя.
  Project nearest наследуется спрайтами; MSAA/экранное сглаживание не включены.
  В legacy глобальный snap transforms выключен; HD включает snap конечных
  2D-трансформаций. Дополнительное округление вершин не включалось.

## Происхождение чёрных полей

Старый integer stretch выбирает `floor(min(window_width/480, window_height/270))`.
Например, 1600×900 превращается в изображение 1440×810 с полями 80/45 пикселей
с каждой стороны; 1280×1024 — в 960×540 с полями 160/242. Это воспроизведено
на настоящем окне и измерено по чёрной рамке снимка.

Особенно заметен эффект, если оконный менеджер уменьшает клиентскую область
из-за панели и заголовка: **расчётный пример**, 1920×1044 вместо запрошенных
1920×1080 уже снижает масштаб с ×4 до ×3, даёт 1440×810 и поля 240/117.
Сам `window_width_override` не гарантирует фактический размер клиентской области.
Исходные скриншоты из формулировки задания не приложены, поэтому их точный
размер и возможные внешние рамки просмотрщика установить нельзя.

При фактических 1920×1080 у legacy полей нет: захват полностью совпал
с viewport, увеличенным nearest ×4. Увеличение одного viewport до 960 без
смены политики сделало бы поля больше: например, ×2 и 56,25% заполнения при 2560×1440.

В HD выбран максимальный прямоугольник 16:9. Если его коэффициент целый,
используется integer; иначе fractional с тем же nearest. Так 1920×1080 даёт ×2,
1600×900 — ×5/3, 2560×1440 — ×8/3, 1280×1024 — изображение 1280×720
и только необходимые поля по 152 сверху/снизу. Legacy сохраняет старую политику
integer для обратимости сравнения.

**Ограничение:** одновременно полностью заполнить 1600×900 или 2560×1440,
сохранить весь viewport 960×540 и одинаковый целый размер каждого пикселя
математически невозможно. Nearest не смешивает цвета, но при дробном коэффициенте
ширина пикселей чередуется. Ниже 960×540 часть деталей пропадает при уменьшении.
Для равномерного пикселя предпочтительны 960×540, 1920×1080, 2880×1620.

## Изменения

`PixelDisplay` выбирает размер корневого viewport и способ вписывания окна;
`App` подключает его только для графического клиента. Dedicated server не затронут.
В viewport stretch сигнал `Viewport.size_changed` может не сообщать об изменении
только физического окна: небольшой узел сравнивает размер окна каждый кадр
и пересчитывает режим лишь при изменении.

`GameScreen.apply_settings()` умножает zoom камеры на 2 только в HD.
Мировые узлы и ресурсы не масштабируются дополнительно. Мир 480×270 мировых
пикселей занимает растр 960×540. Поэтому клетка 16 мировых пикселей становится
32 логическими и затем 64 физическими пикселями в окне 1920×1080.

HUD сохраняет собственный scale 1: шрифт 16 в HD становится 32 физическими
пикселями вместо 64 у legacy. Верхние строки разведены, ограничены шириной
с многоточием; миникарта привязана к правому краю, хотбар центрируется по своей
фактической ширине, status привязан к нижнему краю. Дизайн панелей не переделывался.

## Реальные захваты и измерения

Godot 4.7.2 stable, Compatibility/OpenGL, X11, Mesa llvmpipe. Xvfb 2560×1440
и отдельный xfwm4 позволяют действительно менять окно и переходить в fullscreen,
не изменяя рабочий стол пользователя. Стенд загружает **основную сцену**,
создаёт временный профиль, подписанного персонажа и обычный локальный мир seed=1.
Дом строит существующий игровой `--demo`, через обычные запросы сервера;
деревья и ландшафт создаёт настоящая генерация мира. Профиль default не читался
и не изменялся. Профили стенда записываются только в `/tmp`.

`*-viewport.png` — прямой логический растр после `frame_post_draw`.
`*-window.png` — физические пиксели настоящего X11-окна через
`DisplayServer.screen_get_image`, с сохранением полей Godot. Окно стенда без
декораций; рамка рабочего стола в игровой размер не входит.
Изображения окна не увеличивались для имитации заполнения.

| Логический viewport | 480×270 | 960×540 |

| Клетка в симуляции | 256×256 | 256×256 |

Рост измерен отдельной прозрачной маской точных слоёв текущего персонажа,
без оружия, в одинаковой южной idle-позе. Разница 128/126 возникает при
растрировании исходного изображения с scale 0,5 и 1 после камеры, а не от изменения
мирового размера. Высоты окружения в таблице — полные атласные прямоугольники,
включая прозрачные поля; они не выданы за высоты непрозрачных силуэтов.
Прозрачный SubViewport используется только для этой маски, не для игры.

[сырые параметры и проверки](measurements.json), [проверка растров](verification.json).
В дробных режимах колонка «рост × масштаб» — геометрическая величина;

## Проверки

```sh
tools/run_tests.sh
tools/run_tests.sh --only=test_pixel_display
tools/check_pixel_display.sh
python3 tools/verify_pixel_display.py
```

Для оконного стенда нужны Xvfb, xfwm4 и xprop; Python-проверка использует Pillow и NumPy.
`asset-sha256.txt` — зафиксированные перед изменениями хэши всех 351 файла
`content/` и `assets/`. Они сверены после эксперимента.

Автоматические тесты охватывают выбор размера и политики вписывания, возврат
legacy после HD, одинаковую обзорность при view_zoom 1 и 0,75, границы HUD.
Оконный прогон проверяет все восемь направлений, одинаковые перемещения в
симуляционных единицах, совпадение округлённых позиции камеры и ног на каждом
кадре, закрытую дверь, наведение реальной мыши на дверь, E/проход, G/подбор
камня, ввод C/I/B/M, resize и fullscreen, возврат HD → legacy в одном процессе.
Растровая проверка сверяет 28 пар viewport/окно с nearest и фактические поля.
В 1920×1080 совпадение с nearest ×4/×2 строго попиксельное.

Результаты запусков: [tests.log](tests.log), [focused-tests.log](focused-tests.log),
[runtime.log](runtime.log), [capture-check.log](capture-check.log).
Окончательный общий прогон: **222 теста, 0 проваленных проверок, 127,6 с**;
отдельно четыре новых теста — 0 провалов. Оконный прогон — **188 проверок**,
растровый — **28 пар**; все прошли. Две ожидаемые ошибки ENet общего прогона
создаются существующими тестами занятого порта и учтены раннером.
Допустимое предупреждение llvmpipe о невозможности переключить vsync остаётся
в runtime.log; это не ошибка скрипта.

## Границы результата и следующий этап

В стандартном zoom 1 камера и персонаж используют одну мировую целочисленную
сетку; в HD она даёт шаг 2 логических пикселя. Дополнительных дробных смещений
камеры не добавлено. При дробном физическом выводе возможна неравномерность
шага пикселей. Отдаление 0,75 уже само по себе дробное относительно исходных
текстур; здесь проверено сохранение его обзорности, не равномерный пиксель.

Это проверка корректности отображения, не бенчмарк GPU: растр стал в четыре
раза больше по площади. Прогон выполнялся программным рендерером; native GPU,
Windows, высокое DPI и длительные игровые сессии отдельно не проверялись.
Универсальная адаптация всех локальных координат модальных панелей не делалась.

Для будущих исходников 32×32 нужно сохранить клетку 16 **в мире презентации**,
256 **в симуляции**, и отображать 32 текселя на эти 16 мировых пикселей,
затем camera ×2 получит 32 логических пикселя. Персонаж с видимыми 64 текселями
аналогично использует pixel_scale 0,5 и pivot в координатах источника.
У текущего human_m такой масштаб уже есть: HD использует больше деталей
существующего 96×96 источника без его изменения.

Простая замена 16×16 файла на 32×32 недостаточна: WorldView сейчас назначает
`texture_region_size=16`, а окружение не имеет общего pixel_scale. Следующий
отдельный этап должен ввести перевод текселей/опор в мировые размеры для
атласов и TileMap, не менять Movement.UNIT, сеть, reach или сохранения.
Этот этап не начат. Окончательный переход также потребует выбора политики
для дробных физических размеров и проверки производительности на целевом GPU.

Рекомендация: принять **960×540 как пригодную экспериментальную основу**,
с эталонным режимом 1920×1080 ×2; оставлять legacy доступным до нового этапа.
Создание ассетов и изменение художественного стандарта требуют отдельного решения.
