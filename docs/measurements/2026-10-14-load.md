# Нагрузочное испытание сервера (сценарий 20 GDD) — 14.10.2026

**Машина:** та же, что в `2026-10-14-storage.md`: Xeon E5-2680 v4, SATA SSD, Godot 4.7.2.
**Как повторить:** `tools/run_tests.sh --bench --only=bench_load` (≈ 2 мин).

- **Сервер** — `src/server/server_main.gd` отдельным процессом, ENet, `--stats=5`.
- **Боты** — `tests/support/load_bots.gd`, отдельный процесс; каждый бот — настоящий `GameClient` по ENet на localhost.
- **Поведение ботов:**
  - меняют направление каждые 0,8–3 с;
  - каждые 2–6 с делают действие: строят стену (40%), разбирают (30%), бросают камень (15%) или подбирают (15%).
- **Длительность** — 60 с на прогон.

## Результаты (после оптимизаций ниже)

| | 10 игроков | 20 игроков |
|---|---|---|
| Тиков в секунду | 20,0 | 20,0 |
| Время тика сервера, худшее p99 по 5-секундным окнам | 12,5 мс | 23,5 мс |
| Максимальный тик | 12,5 мс | 23,5 мс |
| Задержка ответа на действие: p50 / p99 / max | 98 / 108 / 109 мс | 104 / 185 / 266 мс |
| Исходящий трафик сервера на одного клиента | 3,8 КБ/с | 6,3 КБ/с |
| Действий за прогон / без ответа | 151 / 0 | 301 / 0 |

Бюджет тика — 50 мс. При 20 игроках занято около половины, остальное — запас на будущие системы (NPC, природа, бой).

- **Задержка ответа** ≈ 2 тика: действие применяется в ближайший тик, ответ уходит после фиксации пакета на диске.
- **Коррекции предсказания у ботов** (55–60 за прогон на всех): мир меняют другие игроки — чужая стена появляется у бота на пути раньше, чем до него дошёл обновлённый чанк. На чистой сети без чужих изменений коррекций нет (`test_prediction_matches_the_server`).

## Что нашли и исправили

| Проблема | Было | Решение | Стало |
|---|---|---|---|
| Кодирование чанков для рассылки в потоке симуляции | пики тика до 78–129 мс при входе игроков | Чанки из базы отдаются байтами как есть; новые кодирует поток загрузки | синхронных загрузок в работе — 0 |
| Снимки собирались для каждого клиента заново, со сравнением по полям | ~20 мс тика при 20 игроках | Общая для всех клиентов реплика с версиями «горячей» и «холодной» части; база снимка хранит только версии | — |
| Детерминированный CBOR для сетевых сообщений | 590 мкс на снимок | Быстрый режим CBOR без сортировки ключей — только для сети; подписи и хранение по-прежнему детерминированы | 267 мкс |
| UUID как ключи сущностей в каждом снимке | 1074 байта на снимок | Короткие номера сущностей на соединение, полный ID — один раз при появлении (протокол v3) | 340 байт; трафик в 2,7 раза меньше |
| Предзагрузка и рассылка чанков пересчитывались каждый тик | 2–2,6 мс тика | Только когда игрок сменил чанк или в обзоре изменился чанк | 0,1–0,7 мс |
| Цикл сервера по сумме кадровых `delta` | — | Абсолютное время тиков, сон между ними | ровно 20 Гц, ядро не занято впустую |

## Где запас дальше

- **Снимки** — всё ещё самая дорогая часть (около 12 мс тика при 20 игроках). Следующие шаги: реже слать дальние сущности, кодировать координаты дельтой, нативный кодек сообщений (GDExtension), если понадобится.
- **Разбор входящих сообщений** (`network_in`, около 2,6 мс при 20 игроках) — CBOR на GDScript. Тот же путь.
- **Повторить замеры на целевом железе сервера** и через настоящую сеть (задержки, потери), а не localhost.
