# Предложение 002 — сеть, хранилище мира, идентичность

**Дата:** 14 октября 2026 · **Статус:** на обсуждении.
Продолжает предложение 001 по замечаниям автора: «свой протокол поверх ENet» и «JSON с журналом для всех сохранений» требуют отдельного разговора. Идентичность (ADR-0003) здесь расписана в деталях.

---

## 1. Сеть

### Что я имел в виду под «своим протоколом»

**Не свой транспорт.** Надёжность, порядок, фрагментацию, каналы и соединения делает ENet внутри Godot. «Своё» — только три вещи над ним:
1. **Формат сообщений** (компактный бинарный, с версией протокола).
2. **Репликация мира:** кому что отправлять (интерес-менеджмент) и как (снимки и дельты).
3. **Запросы клиента** с `request_id` и ответы сервера.

Эти три вещи пришлось бы писать в любом варианте, потому что межлокационная видимость «крыша ↔ улица» — особенность именно нашей игры.

### Варианты

| | Как устроено | За | Против |
|---|---|---|---|
| **N1. Встроенная репликация Godot** (`MultiplayerSpawner`, `MultiplayerSynchronizer`, RPC на узлах) | Каждая сущность — узел, синхронизируются свойства узлов | Быстрый старт, мало кода | Требует узлов на сервере для каждой сущности — противоречит ADR-0002. Видимость задаётся по узлу и пиру: тысячи сущностей во многих локациях — тяжело. Нет дельт для чанков. ID — пути узлов, а не наши постоянные ID |
| **N2. MultiplayerAPI + ENet как транспорт, наши сообщения поверх** | Один сетевой узел с несколькими `@rpc`-функциями, передающими `PackedByteArray`; репликация, интерес и дельты — наши | Соединения, каналы, надёжность — готовые; транспорт заменяем (WebSocket/WebRTC тем же API); полный контроль над тем, кто что видит | Репликацию пишем сами (это и есть ядро сетевой части игры) |
| **N3. Сырой `ENetConnection`** | Пакеты напрямую в ENet | Чуть больше контроля (лимиты полосы, сжатие по каналам) | Теряем абстракцию `MultiplayerPeer`, выигрыш мал |
| **N4. Сторонние решения** | netfox — предсказание и откат для узлов; Nakama — бэкенд (аккаунты, хранилище, матчмейкинг); Steam networking | netfox хорош для шутеров на узлах; Nakama может пригодиться как «центр идентичности», если Q-02 решится так | netfox опирается на узлы (N1); Nakama не запускает нашу симуляцию; Steam — привязка к платформе |

### Рекомендация: N2

- **Каналы:**
  - 0 — надёжный упорядоченный (запросы, ответы, события);
  - 1 — ненадёжный последовательный (снимки движения);
  - 2 — надёжный для потоковой выдачи чанков и локаций (низкий приоритет).
- **Снимки:** около 20 Гц, квантованные позиции, дельта к последнему подтверждённому клиентом снимку. Ввод от клиента — 30–60 Гц, со своим предсказанием движения.
- **Интерес клиента:**
  - текущая локация;
  - для наружных позиций (крыша, настил) — ещё и поверхность в радиусе обзора;
  - наружные игроки на крышах рядом видны с улицы.

  Закрытые этажи посторонним не рассылаются.
- **Рукопожатие:** версия протокола, отпечаток набора контента, вход по ключу (раздел 3).
- **Тесты:**
  - транспорт в памяти (быстро, детерминированно);
  - настоящий ENet на localhost в одном процессе — Godot позволяет завести несколько `MultiplayerAPI` на разных ветках дерева;
  - нагрузочный стенд с N клиентами и замерами.

## 2. Хранилище мира

Замечание автора верное: для огромного постоянно меняющегося мира JSON-файлы — плохой выбор. Они большие, медленно разбираются, дают тысячи мелких файлов и не умеют транзакций. **JSON остаётся для описания контента**, конфигов и отладочных выгрузок, но не для состояния мира.

### Что хранится

| Данные | Объём | Как меняется |
|---|---|---|
| Чанки поверхности (клетки: грунт, растительность, части построек) | Много, растёт с исследованием | Редкие точечные правки |
| Локации (этажи, пещеры) | Много | Редкие правки |
| Сущности (NPC, животные, предметы на земле, контейнеры) | Тысячи | Часто (позиции, потребности) |
| Персонажи: `WorldCharacterState`; профили — отдельно от мира | Десятки–тысячи | Часто |
| Права, владение, правила мира | Мало | Редко |
| Ключи идемпотентности подтверждённых операций | Скользящее окно | Постоянно |

### Варианты

| | За | Против |
|---|---|---|
| **S1. JSON-файлы + журнал** (было в 001) | Читаемо | Размер, скорость, нет транзакций — **отклоняю** |
| **S2. Свои регион-файлы с бинарными чанками** (как Anvil в Minecraft) | Компактно, без зависимостей | Защиту от сбоев, журнал, индекс и сжатие файла пишем сами — фактически маленькая СУБД, которую надо поддерживать годами |
| **S3. SQLite как контейнер + бинарные чанки внутри** | Транзакции и восстановление после сбоя (WAL) даром; один файл на мир; индексы (сущности по локации и чанку, владение по `character_id`); резервная копия на ходу (`VACUUM INTO`); миграции схемы в транзакции | Зависимость от GDExtension `godot-sqlite` (MIT, активно развивается: v4.9, август 2026). Если проект заглохнет — это тонкая обёртка над SQLite, соберём сами |
| **S4. Встраиваемое KV (LMDB, RocksDB)** | Быстрая запись | Своя GDExtension, нет запросов — избыточно |

### Рекомендация: S3 — SQLite с бинарными чанковыми данными

Это сочетание обоих вариантов, которые назвал автор.

- **Чанк (32×32 клетки) — бинарный блок:**
  - заголовок (метка формата, версия кодека);
  - **палитра чанка** — список строковых ID контента, встреченных в этом чанке;
  - слои как массивы индексов в эту палитру;
  - разреженные свойства клеток;
  - сжатие zstd (встроено в Godot).

  Благодаря палитре числовые индексы не глобальны: изменения набора контента не ломают старые чанки.
- **Сущности — детерминированный CBOR** (стандартный бинарный формат, читается внешними инструментами, например Python `cbor2`) с версией схемы типа сущности.
- **Встроенный `var_to_bytes` Godot не используем** для долгоживущих данных: формат принадлежит движку, а сохранения живут дольше версий движка.
- **Инструмент `world_dump`** — выгрузка мира или чанка в читаемый JSON для отладки.

### Надёжность записи

- **Мир живёт в памяти сервера; база — его надёжная копия.**
- **Подтверждённые операции** (постройка, передача и крафт предметов, урон по постройкам): все затронутые записи — чанк, инвентари, ключ идемпотентности — пишутся **одной транзакцией за тик**, и только после неё клиент получает подтверждение. Поэтому после сбоя не бывает ни потерянной подтверждённой постройки, ни удвоенного предмета, и журнал повторять не нужно.
- **Частое неответственное состояние** (позиции, рост растений, потребности NPC) сбрасывается периодически (порядка 30–60 с) и при остановке. Сбой теряет только эти секунды.
- **WAL с `synchronous=FULL`** для транзакций операций — проверим замером, хватит ли скорости.
- **Запись в отдельном потоке:** симуляция отдаёт уже закодированные байты, поток пишет и сообщает о фиксации.
- **Перед миграцией схемы — резервная копия** (`VACUUM INTO`), затем миграция в транзакции.

### Профили персонажей

Профили живут **вне файла мира**:
- на клиенте — в своём хранилище профилей;
- на сервере — в отдельной таблице или файле, с привязкой `character_id` → `WorldCharacterState`.

Файл экспорта `.nhnchar` — детерминированный CBOR с подписями (раздел 3), плюс отладочная выгрузка в JSON.

### Первый шаг до принятия

**Короткий спайк:** подключить `godot-sqlite` к Godot 4.7.2 на Linux и Windows. Замерить запись и чтение 10 000 чанков, транзакции за тик при 20 Гц, `VACUUM INTO` на ходу. Результаты принесу цифрами.

## 3. Идентичность (детали к ADR-0003)

- **`character_id`** — UUID v4 из криптографического генератора.
- **Ключ игрока:**
  - создаётся при первом запуске, хранится в `user://identity/`;
  - его можно экспортировать для резервной копии: **потеря ключа = потеря доказательства владения**;
  - отпечаток (SHA-256 публичного ключа) — ID игрока для серверов;
  - пароль на ключ — позже.
- **Алгоритм:**
  - встроенный `Crypto` Godot 4.7.2 умеет генерировать только **RSA**. Проверено: ключ 3072 бита создаётся 3,6 с (один раз), подпись — 13 мс, проверка — 0,26 мс;
  - Ed25519 компактнее и быстрее, но требует ещё одной GDExtension (libsodium);
  - **рекомендация:** RSA-3072 сейчас, в форматах есть поле `key_alg`, чтобы позже добавить Ed25519 без поломки старых профилей.
- **Вход на сервер:** сервер присылает случайный вызов и свой ID; клиент подписывает их ключом; сервер проверяет. Имя персонажа больше не идентифицирует игрока.
- **Подписи профиля — две разные:**
  - **подпись владельца** — «этот профиль выпустил держатель ключа». Владелец может изменить инвентарь и переподписать, поэтому сама по себе она **не доказывает честность содержимого**;
  - **заверение сервера** (необязательное) — «так персонаж выглядел на моём сервере в момент X», подписано ключом сервера. У серверов тоже появляются ключи, и ID сервера = отпечаток его ключа.

  Принимающий сервер по своей политике решает, чьим заверениям верить. Это и есть будущий ответ на Q-02. **Архитектура его не закрепляет**, но делает возможными все варианты: доверие только своим серверам, сеть доверенных серверов, общий центр.
- **Копирование (Q-01) этим не предотвращается** и не решается.
