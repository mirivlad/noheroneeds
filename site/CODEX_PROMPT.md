# Задание Codex: официальный сайт и живая энциклопедия No Hero Needed

Репозиторий: `https://github.com/mirivlad/noheroneeds`.

## Зачем

Преврати приложенную готовую основу сайта `nhn-pages/` в официальный сайт игры на GitHub Pages (`https://mirivlad.github.io/noheroneeds/`). Сайт должен выглядеть как качественная игровая вики и витрина проекта: главная, энциклопедия, руководство по механикам, история релизов и поиск. **Данные энциклопедии должны обновляться автоматически при изменении игры и контента**, а патчноуты — при публикации релиза. Не ограничивайся генерацией списка предметов: нужны настоящие взаимные связи между добычей, переработкой, рецептами, оборудованием, навыками, чертежами, NPC, торговлей и игровыми действиями.

## Правила работы с репозиторием

1. Создай отдельную ветку `feat/game-site-wiki` на актуальной `main`; подготовь PR. **Не переписывай `main` и не трогай игровую логику, рендер, ассеты и существующий релизный конвейер без необходимости**. Используй вложенную директорию `site/` для исходников сайта и `tools/site/` для генераторов и проверок; при необходимости аккуратно адаптируй раскладку.
2. Перед реализацией изучи содержимое `content/base/*.json`, формат пакетов и дополнительных content packs, игровые сцены/механику и документацию `docs/adr`. Обозначь границы: что можно достоверно вывести из данных, а что требует ручного текстового объяснения механики. Документы ADR — источник принятых правил, но устаревшие проекты/планы не должны маскироваться под работающие возможности. Сверяй с кодом и тестами.
3. Сохрани узнаваемый визуальный язык прикреплённого сайта: тёмная лесная палитра, тёплые золотые акценты, крупные игровые изображения, аккуратная типографика, адаптивность, навигация, поиск. Улучшай дизайн, не упрощай его до стандартной документации.
4. Публикация должна быть на *GitHub Pages*, без PHP, базы, отдельного сервера, внешнего CMS и обязательных runtime-запросов к GitHub API. Результат сборки — полностью статический HTML/CSS/JS/JSON, работающий в подпути `/noheroneeds/`.

## Энциклопедия: реальный игровой контент

**Единый источник истины — игровой контент, не копии ручных списков.** Собирай каталог из всех релевантных пакетов (минимум `materials.json`, `recipes.json`, `professions.json`, `underground.json`, `terrain.json`, `creatures.json`, `characters.json`, `building.json`, `structures.json`, `settlements.json` и актуальных новых файлов). Отдельные дополняемые пакеты не игнорируй. Не выводи лишь записи, уже известные стартовой HTML-версии.

Для каждой сущности с ID делай стабильную адресуемую страницу/ссылку (поддержка `base:...`):

- **Материалы и предметы:** название, назначение, игровой тип, источники получения (растения и их дроп, месторождения, животные, промысел, торговцы), что из них создаётся, обратные ссылки на использующие их рецепты. Для оружия, одежды, инструментов и еды — фактические характеристики из данных; ничего не выдумывать.
- **Геология:** железо, медь, серебро, золото, самоцветы, кремень; поверхность/подземелья, рельеф, глубины и способы добычи; ресурсы не восстанавливаются. Конкретные числовые сведения только когда однозначно поддержаны генератором/данными.
- **Рецепты:** точные входы/выходы и количества, станок, навык и сложность, врождённость, требования, связи с ингредиентами и результатами, учителя с их ценой/доверием/требуемым навыком, чертежи и изучение.
- **NPC/профессии:** где встречаются, чему учат, стоимость и ограничения, базовый ассортимент и выкуп, отличие статического ассортимента от динамической экономики деревень и караванов.
- **Строительство, сельское хозяйство, животноводство, существа, транспорт, бой, потребности, сезоны, погода, взаимодействия:** объяснять игроку, как именно это использовать и что влияет на результат. Связывать объяснения с каталогом; не писать технические ADR прямо на сайте.
- **Двусторонние связи:** из руды → рецепт плавки → слиток → рецепт меча → кузнец/чертёж, а обратно из меча → необходимые материалы → способы добычи.

Обозначай явно, если в игровых данных нет сведений, а не делай предположение. Названия, ID, материалы, требования, значения и торговые предложения должны браться из текущего состояния игры. Отдельно документируй источник каждого динамически собранного поля и возможные ограничения.

## Редакционные руководства по механикам

Создай `site/content/guides/` (Markdown с frontmatter или сопоставимый формат) для поддерживаемых руками текстов: управление, начало с пустыми руками, добыча руд, плавка, ремесло/мастерство, бой, строительство, земледелие, животноводство, рыбалка, море и лодки, деревни и торговля, караваны, разбойники, работа охранником, мультиплеер и условия выживания. В этих текстах должны быть полезные инструкции, а не общие фразы. Связывай каждую упомянутую игровую сущность с машинным каталогом, добавляй изображения из репозитория, если они действительно соответствуют описанию.

Для нового геймплейного действия или механики обязательно **обновление соответствующего руководства в том же PR/изменении**, плюс отражение доступных рецептов/предметов в генерируемом справочнике. Добавь карту покрываемых механик (`mechanics-manifest.json`) с путями к игровым подсистемам, соответствующим страницам и правилами проверки, чтобы пропуск документации обнаруживался автоматически. При изменении механического кода без обновления руководства/манифеста тест должен требовать обоснование `no-player-facing-change` в PR (явно, без молчаливого пропуска). Нельзя заставлять документацию обновляться на любое техническое изменение, не влияющее на игрока.

## Патчноуты — обязательная часть релиза

1. Перенеси подтверждённую историю **всех опубликованных GitHub Releases от v0.1.0 до v0.16.0** и поддерживай её; учти отдельные теги без страницы релиза (v0.2.0 и v0.10.0), не выдавая их за опубликованные релизы.
2. Для новых версий источник — опубликованные GitHub Releases и сравнение соответствующих тегов. Показывай дату, версию, игровые разделы «Новое», «Изменено», «Исправлено», «Мир», если применимо, и прямую ссылку на релиз. Никакого языка внутренних коммитов. Не включай незавершённое и планы. Если release notes слишком скудные, **не фантазируй**: явно требуй от автора пользовательское описание до публикации.
3. Внедри генерацию / обновление патчноутов и Pages на событие `release: published` и сборку на `push main`. Нужны также проверка PR и ручной запуск `workflow_dispatch`. Используй `actions/configure-pages`, `actions/upload-pages-artifact` и `actions/deploy-pages`; корректные `permissions`, `concurrency` и ограничения на fork PR. Не полагайся на commit в ветку `gh-pages`, если лучше работает современное развёртывание Pages через Actions.
4. При подготовке релиза игровой CI должен проверять, что существует понятный игрокам проект описания изменений этой версии (например, `docs/changelog/vX.Y.Z.md` или поле подготовки релиза). Нельзя публиковать пустую или чисто техническую сводку без явного решения автора.

## Автоматическая генерация и тесты

- Сделай детерминированный генератор `tools/site/build.py` (или эквивалент), принимающий путь к корню игрового репозитория. На выходе — данные каталога, обратный индекс связей, поисковый индекс, статические страницы/JSON. Сборка не должна требовать вручную перечислять каждую новую вещь или рецепт. Допустима ручная редактура игровых руководств.
- Тесты: корректная загрузка всех пакетов; уникальные ID; разрешение ссылок; все `inputs/outputs` рецептов существуют; нет осиротевших записей, потерянных рецептов или учителей; точное количество/набор рецептов соответствует игровой базе; все механики из манифеста покрыты; патчноуты отсортированы, имеют прямые ссылки и покрывают опубликованные релизы; нет лишних выпусков; пути под `/noheroneeds/` работают.
- **Регрессионный кейс:** рецепт `base:forge_iron_sword` содержит 3 железных слитка, 1 доску, 1 бечёвку, создаёт меч у кузницы, обучение у `base:smith` — только как пример теста; генератор должен получать это из исходных данных, а не захардкодить на сайте.
- Обязательны браузерные Playwright-тесты: главная → вики → руда → выплавка → слиток → меч → учитель; поиск; 404/пустые результаты; мобильное меню; свет/контраст и адаптивность; история релизов от первого до последнего; клик по **последней** версии подсвечивает именно её и остаётся корректным при прокрутке к самому низу (известный баг 0.13/0.12). Проверки выполняются в CI.
- Проверка `build && git diff --exit-code` для сгенерированных данных при изменении content JSON: изменившийся контент не должен проходить без обновления справочника. Если сайт собирается целиком в CI и артефакты не хранятся в git, проверяй *сгенерированные манифесты* и тестируй соответствие данным без требования коммита build-артефактов.
- Проверяй внешние скриншоты: пути существуют по закреплённому тегу/коммиту либо снимки копируются при сборке. Сохраняй credits/лицензии, не подменяй игровые изображения чужими.

## Приёмка

1. Рабочая главная `index.html`, полноценная вики с поиском и двунаправленными связями, подробный раздел «Как играть», все патчноуты и корректная навигация на мобильном/десктопе.
2. Локальная команда для сборки и просмотра, одна команда тестирования, README по настройке Pages и Actions.
3. CI зелёный; браузерные проверки с реальными скриншотами; preview сборки для проверки.
4. Всё в отдельном PR с перечнем изменённых файлов, тестами, примерами цепочек для железа/меди/серебра/золота, указанием нерешённых пробелов. **Не создавай новый игровой релиз лишь ради сайта.**

Работай самостоятельно, не ограничивайся концепцией или пустыми шаблонами. Если функциональность нельзя подтвердить кодом или данными — не публикуй её как готовую. После PR подготовь краткий отчёт, не меняя `main` до подтверждения.
